# План масштабування до міста-мільйонника (робочий документ для агентів)

Мета гри — містобудівний симулятор рівня Cities: Skylines із **симуляцією населення без агентів** (макромодель TAZ → OD → розподіл) і **сильним муніципальним транспортом** як головною фішкою. Цільовий масштаб: місто 1 000 000+ жителів (≈1 500–3 000 TAZ, 20–50 тис. вузлів доріг, 100–300 ліній ГТ) без проблем продуктивності.

Цей файл — план продовження для наступних агентів: що вже зроблено, що робити далі, як перевіряти. Обґрунтування вибору підходу й заміри — у [scaling-audit.md](scaling-audit.md), архітектура — у [architecture.md](architecture.md).

---

## 1. Обраний підхід (коротко)

**Амортизована потокова макромодель + модель ГТ на рівні зупинок і ліній.**

- Населення — числа в зонах, а не агенти. Масштаб визначає **площа міста** (кількість TAZ `K` і вузлів `N`), а не кількість жителів.
- Пошук шляхів — потоковий: дерево для кожного вузла доступу TAZ будується, пише рядок матриці часу (`TravelTimeSkim`), додає потоки й одразу викидається. Пам'ять O(K²), а не O(K·N).
- Рівновага MSA продовжується між циклами (теплий старт): 1 ітерація на цикл.
- Важка частина перерахунку — у фоновому потоці з подвійною буферизацією; на головному потоці лише коротке застосування результату.
- ГТ — окрема компактна мережа зупинок/ліній із довільною кількістю пересадок, навантаженням ліній і переповненістю.

## 2. Поточний стан (після етапів A, B і C)

Бенчмарк: `Tests/Performance/MetropolisBudgetBenchmark.cs` (місто «Метрополіс»: 1,19 млн жителів, 1 521 TAZ, 37 057 вузлів, 92 544 ребер, 150 ліній; заміри на 16 ядрах).

| Метрика | Бюджет | База (до B) | Після B | Зараз (після C) |
| :--- | ---: | ---: | ---: | ---: |
| Стабільний цикл у воркері | ≤ 1 500 мс | 16 249 мс | 2 194 мс | **~2 500–2 900 мс** |
| Застосування на головному потоці | ≤ 3 мс | 33 998 мс | 29 829 мс | **~41 мс** |
| Пам'ять макромоделі | ≤ 150 МБ | 3 765 МБ | 217 МБ | **~230 МБ** |
| Структурна перебудова TAZ (після редагування), воркер | — | — | ~17 700 мс | **~3 300 мс** |
| Побудова міста | — | ~88 с | 3,5 с |

Розбивка стабільного циклу після C (мс): OD + mode split ~250 · розподіл авто ~1 430 · розподіл ГТ (1 потоковий раунд) ~620 · доступність ~100. Залишок до цілей етапу C: пам'ять (два K² буфери OD, списки попиту MSA, `TransitSkim`) і час воркера (раунд ГТ).

Що зроблено (коміти):
- `d2bc2c8` — етап A: `MetropolisCityGenerator`, `SimulationWorld.CreateMetropolis`, діагностика `LastMacroComputeMilliseconds` / `LastMacroMainThreadMilliseconds`, бенчмарк із бюджетами; виправлено O(N²) побудову графа (кеш ID вузлів/ребер у `RoadGraph`).
- `14bf6e1` — етап B: потоковий розподіл (`TrafficEngine.RunAssignmentRound`), `TravelTimeSkim`, теплий старт (`TrafficEngine.WarmStart`, `MinWarmStepSize = 0.25`), детерміновані чанки (`AccumulationChunks = 16`), один спільний `TrafficEngine` у світі, `OptimizedODMatrix.GetPathTree` на вимогу, авторитетний кеш пересадок у `TazManager`, точні розміри K²-масивів.
- `71dfcec` — етап C (гілка `transit-stop-line-model`): модель ГТ на рівні зупинок і ліній (`TransitNetworkSnapshot`, `TransitSkim`, `TransitEngine`); streaming Dijkstra на розширеному графі зупинок з довільною кількістю пересадок (0, 1, 2+) та пішохідними пересадками між сусідніми зупинками (160 м, `SpatialGridIndex`), BPR-штраф переповненості (>80%); повне видалення `TransitConnectionInfo` та квадратичного перебору з `TazManager`/`TransitManager`; фоновий розрахунок ГТ і просторове бакетування зупинок у `TransitManager.GetTransitCoverage`; час застосування на головному потоці скорочено з 29 829 до **~41 мс** (< 50 мс), структурна перебудова TAZ — з ~17 700 до **~3 300 мс**; детерміноване сумування `TotalTrips` у `OptimizedODMatrix`.

## 3. Наступні етапи

Порядок: **D → (E, F лише якщо бюджети не виконано)**. Кожен етап — окрема гілка, окремі коміти, бенчмарк до/після в повідомленні коміту й таблиці `scaling-audit.md`.

### Етап C — модель ГТ на рівні зупинок і ліній *(виконано в `71dfcec`)*

**Результати:**
- Застосування на головному потоці: **29 829 мс → ~41 мс** (виконано критерій < 50 мс; залишок до ≤ 3 мс зніметься в етапі D).
- Структурна перебудова TAZ у воркері: **~17 700 мс → ~3 300 мс** (прискорення в 5.4×).
- Модель підтримує 0, 1, 2+ пересадок, пішохідні пересадки в радіусі 160 м між зупинками різних ліній, BPR-функцію переповненості сегментів ліній при завантаженні > 80%.
- Видалено застарілий кеш `TransitConnectionInfo` та квадратичний перебір маршрутів у `TazManager` і `TransitManager`.
- Додано юніт-тести нової моделі ГТ (`TransitStopLineModelTests.cs`), усі 365 тестів проходять.

### Етап D — компактний граф маршрутизації *(головний поточний пріоритет)*

**Проблема.** Раунд пошуку ~1,6 с: одна Дейкстра на 37 тис. вузлів ~3,6 мс, паралелізм на 16 ядрах дає лише ~3,4× (обмеження пам'яттю). ~75% вузлів метрополісу — проміжні точки кривих вулиць (ступінь 2). `RoutingSnapshot` індексується сирими ID вузлів до `GetMaxNodeIndex()` (діри після видалень).

**Дизайн.**
1. **Щільні ID** у знімку: відображення `nodeId → dense` при `Rebuild`; масиви пошуку розміром кількості живих вузлів.
2. **Злиття ланцюжків ступеня 2:** вузол, що має рівно двох сусідів (двосторонній ланцюжок) і **не є** вузлом доступу TAZ, зупинкою ГТ чи кінцем тупика, згортається; ланцюжок стає одним «суперребром» із вартістю = сума вартостей ребер (перераховується щораунду за O(E)). Топологію компактного графа будувати лише при зміні `RoadGraph.TopologyVersion` або множини захищених вузлів; вартості — щораунду.
3. **Розгортання потоків:** потік на суперребрі додається до кожного ребра ланцюжка (зберігати список ребер ланцюжка в CSR-масиві). `TravelTimeSkim` працює лише з вузлами доступу — не змінюється.
4. Шляхи для UI (`OptimizedODMatrix.GetPathTree`, `CommuteAnalytics.ExtractPathFromTreeBuffer`) лишаються на повному графі (`RoadGraph`), або розгортають ланцюжки — вирішити при реалізації.

**Критерії готовності.** Раунд пошуку на метрополісі ≤ 500 мс, стабільний цикл воркера ≤ 1 500 мс (бюджет), потоки й скім **ідентичні** (або в межах 1e-4 відносної похибки, якщо змінюється порядок додавання) порівняно з повним графом — тест порівняння на `MetropolisOptions.Small`.

### Етап E — райони для далеких пар (лише якщо K > ~2 500 або бюджет не виконано)

Дворівнева зонна система: TAZ + райони (напр. 4×4 TAZ). Гравітація й логіт для пар далі порогу (за часом) рахуються між районами й розподіляються пропорційно; близькі пари — точно. K² → K·k_близьких + D². Змінює результати моделі — потребує рішення щодо якості й нових еталонів у тестах.

### Етап F — Customizable Contraction Hierarchies / PHAST (лише якщо після D пошук усе ще > 50% бюджету)

Топологічне впорядкування (nested dissection) при зміні топології, кастомізація ваг щораунду, пошук «від одного до всіх» через PHAST (лінійний прохід, SIMD-дружній). Висока складність — братися лише з вимірами, що це виправдовує.

## 4. Беклог поруч із етапами

| Задача | Пріоритет | Примітка |
| :--- | :--- | :--- |
| Детермінований `OptimizedODMatrix.TotalTrips` | Вирішено (C) | Сумування ведеться через `_rowTripSums` у детермінованому послідовному циклі за індексами TAZ. |
| Сценарій «Метрополіс» у меню | Середній | Стрес-тест у грі: `ScenarioType.Metropolis` + `SimulationWorld.CreateMetropolis` у `Main`, кнопка в `MainMenu`. Камера/рендеринг на такому розмірі ще не перевірялися. |
| Щільні ID в редагованій моделі, ущільнення «надгробків» ребер | Низький | Для продуктивності не потрібне, якщо етап D дає щільні ID у знімку. |
| Розв'язка `RoadNode.Id == Zone.Id` для клітинок сітки | Низький | Питання чистоти моделі (інструменти, генератори, ріст), не швидкості. |
| Повне злиття клітинок і парцел | Рішення геймдизайну | Різні правила росту й заторності; спільне вже винесено в `ILandUseUnit`/`LandUse`. |
| Дедуплікація перевантажень `CommuteAnalytics` (зона/парцела) | Низький | Через `ILandUseUnit`. |
| Рендеринг міста-мільйонника | Середній | `CityRenderer`/`RoadRenderer` малюють усе через `_Draw`; на 37 тис. вузлів потрібні чанки/меші й відсікання за камерою. Окремий етап після C/D. |

## 5. Як працювати (для агентів)

**Перед комітом обов'язково:**
```bash
dotnet build CitySim.csproj && dotnet test Tests/Tests.csproj
```

**Бенчмарк бюджетів (явний, ~2–3 хв):**
```bash
dotnet test Tests/Tests.csproj --filter "FullyQualifiedName~MetropolisBudgetBenchmark" --logger "console;verbosity=detailed"
```
Також є `Tests/Performance/MacroPipelineBenchmark.cs` (синтетичні сітки 40×40 / 80×80, розбивка по кроках).

**Перевірка в Godot** (бінарник `godot` 4.7 mono доступний у середовищі):
```bash
timeout 180 godot --headless --path . res://Scenes/Main.tscn --quit-after 2000
```
Скриншот для візуальної перевірки — GDScript поза проєктом (напр. у scratchpad), запуск `SHOT_OUT=/шлях/shot.png godot --path . --script /шлях/shot.gd --resolution 1280x800`:
```gdscript
extends SceneTree
var frames := 0
func _initialize():
	root.add_child(load("res://Scenes/Main.tscn").instantiate())
func _process(delta):
	frames += 1
	if frames == 180:
		root.get_viewport().get_texture().get_image().save_png(OS.get_environment("SHOT_OUT"))
		quit()
	return false
```
Еталон туторіального міста на старті: «Trips: 821/h», модальний спліт 9.8% авто / 14.4% ГТ / 75.8% пішки.

**Правила, які легко порушити** (детально — `AGENTS.md`, `Scripts/Simulation/AGENTS.md`):
- Не кешувати дерева найкоротших шляхів на кожне джерело; паралельне накопичення — лише через фіксовані чанки з детермінованим злиттям.
- Фоновий воркер не пише стан, який читає головний потік щокадрово (`RoadEdge.CurrentVolume`, `TransitRoute`/`TransitStop`); усе публікується в `SimulationWorld.ApplyMacroJob`.
- Будь-яке редагування світу починається з `world.BeginEdit()` (команди й інструменти вже це роблять).
- Зміни топології доріг — лише через `SimulationWorld.ApplyTopologyChange()` / `TopologyChangeCoordinator`.
- Тести за замовчуванням працюють у синхронному режимі; фонову поведінку перевіряти явно (`BackgroundMacroModelTests`) і порівнювати з синхронною.
- Кожен етап: заміри до/після в повідомленні коміту + рядок у таблиці `docs/scaling-audit.md` + оновити розділ 2 цього файлу.
